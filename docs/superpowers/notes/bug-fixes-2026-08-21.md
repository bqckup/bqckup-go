## Bug 1 — CRITICAL: prune bisa menghapus data backup milik site lain

**File:** `internal/engine/restic/repository/prune.go`

Bayangkan repo itu kotak besar. Beberapa site (site-a, site-b) menitipkan
backup di kotak yang sama. Setiap backup menyimpan isinya sebagai
potongan-potongan data (blob) yang dikemas dalam pak (pack).

Prune bertugas membuang potongan data yang sudah tidak dipakai. Aturannya:
potongan yang masih dirujuk snapshot mana pun **wajib dipertahankan**.

Bug-nya: kode hanya mengecek snapshot milik site yang sedang diprune.
Snapshot site lain diabaikan. Akibatnya, data site-b ikut terhapus diam-diam
padahal snapshot-nya masih ada. Backup rusak tanpa peringatan.

Kasus terparah: tag site tidak cocok dengan snapshot mana pun (site
di-rename, typo) → daftar yang dicek kosong → **seluruh isi repo terhapus
dalam satu run**. Seluruh riwayat backup lenyap.

**Cek ke restic asli:** restic menghitung data terpakai dari **semua**
snapshot yang tersisa, bukan hanya sebagian (`getUsedBlobs` →
`ForAllSnapshots`).

**Perbaikan:** setelah snapshot lama dihapus, daftar ulang snapshot yang
tersisa dan tandai semuanya — tag apa pun. Sekarang prune tidak akan
menyentuh data yang masih dirujuk snapshot mana pun.

**Test:** `TestForgetAndPruneKeepsSnapshotsWithOtherTags`,
`TestForgetAndPruneWithUnknownTagDeletesNothing`.
RED: data site lain ikut terhapus / seluruh repo terhapus.

## Bug 2 — HIGH: lock bisa "bocor" dan memblokir repo 30 menit+

**File:** `internal/engine/restic/lock/lock.go`, `facade/facade.go`

Lock = tanda "repo sedang dipakai". Selama backup panjang berjalan, tanda
ini diperbarui (refresh) setiap 5 menit supaya tidak dianggap kedaluwarsa.

Cara refresh bekerja: buat tanda baru, lalu hapus tanda lama. Bug-nya ada
dua:

1. Penghapusan tanda lama memakai context yang bisa dibatalkan. Kalau
   context keburu dibatalkan (atau network error sebentar), tanda lama
   tertinggal. Tandanya masih segar, jadi backup berikutnya menolak jalan:
   "repository is already locked".
2. Saat proses selesai, hanya tanda terakhir yang dihapus. Tanda yang
   tertinggal tadi tidak pernah dibersihkan. Repo terkunci minimal 30 menit
   (sampai tandanya kedaluwarsa) dan butuh intervensi manual.

**Cek ke restic asli:** restic menghapus tanda lama dengan context baru
yang tidak bisa dibatalkan (`context.TODO()`), dan kalau refresh gagal,
restic hanya mencatat peringatan lalu **mencoba lagi** — tidak menyerah.

**Perbaikan:**

- Hapus tanda lama dengan context yang kebal pembatalan.
- Catat **semua** tanda yang pernah dibuat proses ini. Saat selesai, hapus
  semuanya — termasuk yang sempat bocor.
- Refresh yang gagal tidak menghentikan loop refresh. Nanti dicoba lagi.

**Test:** `TestRefreshRemoveFailureDoesNotLeakLock`,
`TestRefreshOldLockRemovalSurvivesCancellation`.
RED: tanda lama nyangkut dan memblokir lock berikutnya.

## Bug 3 — MEDIUM: metadata artifact incremental

**Status: TIDAK DIPERBAIKI — bukan bug.**

Laporan bilang kolom `SHA256` berisi snapshot ID, bukan hash objek. Setelah
dicek:

- Dokumen keputusan desain (`restic-product-decisions.md` §6) memang
  menetapkan ini: `SHA256 = snapshot ID, Size = DataAdded`.
- Secara teknis snapshot ID restic **adalah** SHA-256 dari objek snapshot
  itu sendiri. Jadi kolomnya tidak bohong.

Kalau ingin diubah, itu perubahan keputusan desain, bukan perbaikan bug.

## Bug 4 — MEDIUM: dua run di detik yang sama, run kedua gagal total

**File:** `internal/storage/storage.go`

Folder tujuan backup dinamai dari waktu run, dengan resolusi 1 detik:
`2026-08-21T10-42-19Z`. Storage menolak menimpa objek yang sudah ada
(write-once — memang disengaja, demi keamanan).

Masalah: jalankan `backup run --force` dua kali berurutan (atau cron +
manual bersamaan) dalam detik yang sama → nama folder sama → run kedua
gagal: "could not store backup artifact".

**Perbaikan:** resolusi dinaikkan ke nanodetik:
`2026-08-21T10-42-19.123456789Z`. Dua run harus mulai di nanodetik yang
sama persis untuk bertabrakan — mustahil dengan jam sungguhan.

**Test:** `TestPutSameSecondRunsDoNotCollide`.
RED: error persis seperti laporan ("already exists").

## Bug 5 — LOW: hard link tidak didedup

**Status: TIDAK DIPERBAIKI — bukan bug.**

Laporan bilang restic asli menyimpan konten hardlink sekali saja. Cek ke
source restic 0.16.4: archiver-nya **tidak** dedup hardlink (fitur itu
cuma ada di restorer). Dedup tetap terjadi di level blob: konten sama →
ID blob sama → tersimpan sekali. Jadi tidak ada ruang terbuang, hanya
chunking ulang yang boros sedikit CPU. Perilaku kita sudah sama dengan
restic asli.

## Bug 8 — LOW: run bisa menggantung berstatus "running" selamanya

**File:** `internal/backup/runner.go`

Saat backup selesai, `FinishRun` menulis status akhir ke history. Jalur
gagal sudah memakai context yang kebal pembatalan; jalur sukses belum.
Kalau context dibatalkan tepat setelah backup selesai, `FinishRun` gagal →
baris history menggantung di status "running" selamanya.

**Perbaikan:** satu baris — jalur sukses juga memakai
`context.WithoutCancel(ctx)`.

**Test:** `TestRunnerSuccessFinishRunSurvivesLateCancellation`
(pembatalan disuntikkan tepat setelah operasi storage terakhir).
RED: `FinishRun` melihat context yang sudah dibatalkan.
